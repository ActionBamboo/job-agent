# JobMatch Agent · 面试讲解稿

> 一份「AI 应用 / LLM 应用 / Agent 工程师」岗位可用的作品讲解提纲。对着它把项目讲清楚，比单纯贴简历有效得多。

## 一句话介绍

一个展示 **AI Agent 工程能力** 的求职助手：上传简历 → 抓取/录入岗位 JD → LangGraph 编排的「简历×JD 匹配评分 + 定制打招呼语 + 简历优化建议」，含 Web 看板。**它自己就是一件可演示的作品。**

## 架构

```
浏览器(Web 看板) ──HTTP──▶ FastAPI ──▶ 简历解析(LLM)
                              │              │
                              │              ▼
                              │        结构化简历
                              ▼
                        LangGraph 状态机
                     evaluate(5维打分)
                        ├──▶ tailor(定制话术)
                        └──▶ advise(简历建议)
                              │
                              ▼
                     SQLite 持久化(岗位 + 匹配历史)

抓取源(可插拔): BOSS直聘(Playwright) / 样例JSON / 手工录入
```

## 技术栈

Python 3.12 · LangGraph · LangChain · FastAPI · SQLite · DeepSeek(OpenAI 兼容) · Playwright · PyMuPDF/python-docx

## 核心亮点（面试时可展开）

1. **Agent 编排**：用 LangGraph 状态机做 `evaluate → (tailor ∥ advise)` 并行，而不是写 if/else 面条代码；节点有明确输入输出，天然可测试、可扩展。
2. **工具/模块化设计**：抓取、解析、匹配各自是独立模块；抓取源做成可插拔（换 BOSS→猎聘 只换一个模块），这是「工具调用」思想的工程落地。
3. **LLM 结构化输出**：靠 Prompt 约束 + 稳健 JSON 解析（去代码围栏、取首尾大括号、异常兜底），不依赖特定厂商的 function-calling，兼容任意 OpenAI 兼容接口。
4. **持久化**：SQLite 存岗位与匹配历史，匹配结果跨进程累计，可回看、可做趋势分析。
5. **工程细节**：演示模式（无 Key 跑通全流程）、文件上传（PDF/DOCX/MD/TXT）、CORS、错误处理、路由顺序陷阱的修复。

## 面试高频问题 + 回答要点

**Q1：为什么用 LangGraph，而不是手写一个循环调 LLM？**
A：状态机把「每一步的输入/输出」显式化，便于并行（tailor 和 advise 无依赖可同时跑）、便于加节点（如加「否决规则」）、便于加 checkpointer 做断点续跑；比手写循环更可维护、可测试。

**Q2：怎么保证 LLM 返回的是合法 JSON？**
A：三层——① Prompt 明确要求「只返回 JSON」；② 解析时去 markdown 围栏、正则取首尾大括号；③ 解析失败抛错并让上层重试/兜底。并说明这样设计是为了不绑死某家厂商的 function-calling。

**Q3：匹配评分怎么设计的？**
A：不是让模型拍脑袋给一个总分，而是拆成 5 个维度（技能/经验/职级年限/行业/学历）分别打分 + 一句话理由，再加综合分、匹配亮点、差距点——结构化输出让评分「可解释、可复核」。

**Q4：招聘平台有反爬，怎么办？**
A：用 Playwright 接管真实 Edge（持久化登录态）、串行低频抓取、详情页限流；检测到验证码/登录墙就安全停止，不硬碰。强调「合规 + 低频」意识（这也是加分项）。

**Q5：怎么扩展成自动投递？**
A：在 advise 之后加 `deliver` 节点即可，但投递有封号/ToS 风险，demo 刻意停在「生成话术 + 人工确认」，把最终决定权留给人——这个边界意识本身就是加分点。
